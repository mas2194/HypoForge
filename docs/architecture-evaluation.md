# HypoForge の評価: 実装で確認できる範囲と未検証の主張

## 要約

この文書は、README のアーキテクチャ説明を src/evaluator/pareto.ts、src/phases/adaptive-scheduler.ts、src/phases/review.ts、src/evaluator/runner.ts の実装と照合し、関連するソフトウェア工学研究と比較する。評価対象はリポジトリ上で確認できる設計と機能であり、エンドツーエンドの有効性や研究上の優先性ではない。

現時点で根拠をもって述べられるのは、HypoForge が複数の既知の考え方を一つの開発エージェント・ハーネスに組み合わせていること、そしていくつかの検証・選別機構が実装されていることだ。README は多くの利点を述べるが、比較実験や運用データは提示していない。したがって「最小差分の罠を体系的に排除する」「修正品質を向上させる」「安く有益な実験を先に行う」といった効果は、実装の説明からは導けず、未検証である。

この調査は限定的な先行研究確認であり、網羅的なシステマティックレビューではない。「この組み合わせが世界初」などの新規性は判定しない。

## 評価軸

1. **実装の存在** — 指定ファイルのコードが、README の機構説明に対応するか。
2. **方法上の新規性** — 個別の手法が既存研究ですでに知られているか。新規性と、複数手法を統合した実装上の特徴を区別する。
3. **効果の証拠** — 効果を比較条件、タスク、指標、結果で評価した実験が提示されているか。
4. **主張の限界** — 実装上の簡略化、フォールバック、入力条件が、どの結論を制限するか。

## 新規性の主張をどう限定するか

現状の証拠は、**既知のエージェント制御、ベースライン相対検証、候補選別、コスト考慮スケジューリング、独立レビューを一つのリポジトリにまとめた設計**を記述する根拠になる。これは実装上の統合の説明である。

現状の証拠だけでは、次の主張は支持されない。

- HypoForge が既存エージェントより修正成功率、品質、速度またはコスト効率に優れる。
- 多段階の検証やクリーンルームレビューが、通常のテストや単独レビューより多くの欠陥を発見する。
- スケジューラが同一予算下で情報獲得を増やす、または総実行コストを下げる。
- 介入ラダーや多様性ゲートが、より単純な候補生成より良いアーキテクチャを見つける。
- これらの要素の組み合わせが先行研究・実運用システムで未発表または唯一である。

READMEにある「Minimal-Diff Trap を体系的に排除する」といった表現は、機能目標として読むのが妥当であり、実証結果として扱うべきではない。さらに、その問題設定への対応が常に大規模変更を優先するわけでもない。pareto.ts は追加行数を有利な方向へ直接評価しているため、READMEの目的関数の説明とコードには緊張がある。

## 未検証の主張を検証する実験案

効果を主張するには、同じ課題集合、モデル、トークン・時間予算、実行環境を使った対照実験が必要となる。少なくとも次を事前登録する。

1. **エンドツーエンド比較** — HypoForge と、単一候補の標準的なエージェントフローを同一課題で比較する。主要指標は受理テスト通過率、回帰率、実行時間、API費用とする。
2. **アブレーション** — スケジューラ、Pareto選別、独立レビュー、多層オラクルを一つずつ無効にし、各機構の限界効果を測る。
3. **スケジューラの比較** — 現行の固定コスト/エントロピー順位を、FIFO、ランダム、実測コスト順位、適切な逐次バンディット基準と比較する。実測情報獲得と総コストを記録し、介入レベル別の固定秒数を履歴から校正する。
4. **レビュー品質評価** — 同一差分の完全版と8,000文字制限版、Codexレビューとフォールバックを区別し、既知欠陥の検出率と誤警告率を測る。
5. **統計と再現性** — 複数モデル・複数シードで反復し、信頼区間を報告する。失敗・棄却候補も含め、実行構成と課題データを公開する。

これらの結果が得られるまでは、READMEの機構一覧は**実装の説明**、効果に関する文は**検証仮説**として明確に分けるべきである。
